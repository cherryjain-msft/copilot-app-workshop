LESSON 01 · 15 MIN · READ-ONLY

Your first safe session

Learn what an agent session can do, what it can access, and how to ask a question you can verify.

By the end: you can distinguish session mode from tool permissions and explain a small function using evidence from the actual files.

Understand the controls before the prompt

A chat is useful for exploring an idea. A repository session gives the agent a working context where it can read files, propose changes, run commands, and use approved tools. It is not limited to answering questions. Your prompt should name both the goal and the boundary.

Mode: how you collaborate

Plan asks for a plan before execution. Interactive lets you steer the work together. Autopilot allows more autonomous progress. Start with Interactive or Plan while learning.

Permissions: which tools can run

Tool permissions are separate. Start with Ask every time for this exercise. Read approval requests: a read, a file edit, and a remote push have different effects. A mode is not a security sandbox.

Try it

  1. Finish the practice setup. Create a session in that repository with This computer, New worktree, and the baseline main branch.
  2. Choose Interactive and review Tool permissions → Ask every time. Do not approve an unexpected write.
  3. Send the prompt below. Open each referenced file and check at least one claim yourself.
  4. Open Changes. It should be empty. A good explanation did not require a code edit.
COPILOT PROMPT · READ-ONLY
Read booking-policy.js and booking-policy.test.js in this worktree.
Explain when canCancelOnline returns true and how the tests support that explanation.
Use file and line references. Separate current behavior from the desired behavior in change-request.md.
Give two concrete input/output examples and one question I should ask before changing the rule.
Do not edit files, commit, push, create issues or PRs, or contact external services.

Why this prompt works

It supplies a task (explain), sources (two files), an output (examples and evidence), and a boundary (no writes). Reuse those four elements rather than memorizing the exact wording.

Worked example — compare after your attempt

The baseline allows a booked appointment with 24 hours remaining, but rejects one with 6 hours remaining. The desired rule would allow the 6-hour appointment. Canceled and checked-in appointments stay ineligible. A useful clarification is whether exactly 2 hours is allowed; the change request says yes.

This is an illustrative answer, not evidence that your agent read the files or ran tests. Its file references must match your checkout.

Before moving on

  • You found the cutoff in the file, not just in the agent's answer.
  • You can explain why baseline tests pass while a new requirement is unmet.
  • The worktree has no changes.
Quick check: does selecting Plan mode remove the need to inspect tool permissions?

Mode controls the workflow. Permissions govern tool approvals. Review both; a read-only prompt also states your intent but is not an access-control mechanism.

LESSON 02 · 35 MIN · PROJECT + SESSION

Run a Copilot Project, not just a chat

Give Copilot an ongoing goal, relevant repositories and Library sources, then steer the work as it moves through sessions and decisions.

By the end: you can decide when to use a Project, configure its working context, delegate a bounded session, and use Overview to decide what needs attention.

Project, repository, session, Library: different scopes

A Copilot app Project coordinates an ongoing goal across repositories, sessions, artifacts, and recurring tasks. A repository supplies code and its Git history. A session carries out one task in a chosen environment. The Library holds reference material you add and artifacts created during work. Projects can also investigate material without a code repository.

This is the Copilot app's Project feature, not a GitHub Projects board. Projects are in public preview. Use one for a continuing multi-step goal; use a session directly for a single, self-contained task in one repository.

YOUR PRACTICE QUESTION

Why do customers get different cancellation answers?

The new policy allows booked appointments to be canceled at least 2 hours before the start, with no fee. The kit contains a policy brief, fictional observations of three surfaces, and four feedback records. The observations are supplied evidence, not live API or website checks.

Try it

  1. Create a Project named Cancellation clarity. Add the extracted practice repository when prompted; a Project may also start without one.
  2. Open Library → Add → Add folder. Add only the extracted kit's library folder. Check that the three files are visible.
  3. Send the prompt below from the Project. Open the output and trace each row to the named policy rule and observation.
  4. In the same Project, ask it to propose one separate Plan-mode session for the policy change. Check the repository, starting branch, task boundary, and tests before approving that work.
  5. Return to Overview. Inspect Needs input, Open, Working, and Done; open a session to review its plan, conversation, changes, or PR.

Operate the Project as work progresses

  • Start with a focused goal. In the initial Project prompt, state the desired outcome, first task, constraints, and evidence you expect. Do not paste a vague team mission and expect a safe implementation plan.
  • Add only relevant context. Choose repositories and Library files deliberately. Label which source is authoritative and which is an observation, an assumption, or historical data.
  • Break work into reviewable sessions. Ask for a read-only map first, then propose sessions with clear ownership, files, tests, and dependencies. Independent tasks may run separately; dependent work needs an explicit order.
  • Steer from Overview. Resolve Needs input items; inspect active sessions and their actual plans and diffs. In the session, use Steer this session to give a precise correction. "Done" means a session completed, not that a PR was approved or merged.
  • Keep the Project current. Add new evidence when it arrives, question stale artifacts, and ask a precise follow-up in the same Project. Do not treat prior summaries as a replacement for checking current sources.
Instructions are not acceptance criteria. App instructions apply across sessions; repository instructions apply to sessions for that repository. A Project goal describes the ongoing outcome, and a session prompt describes the next task. The issue's actual requirements and repository evidence still need to be checked.

Before moving on

  • All findings have traceable sources; missing evidence is explicit.
  • F4 remains a feature request, not a bug.
  • You can explain why a newer policy outranks an outdated help article.
Quick check: the policy says 2 hours and an article says 48 hours. What should the agent do?

Source authority is a rule you provide, not a vote among documents. Keep conflicting evidence visible instead of blending it into an invented requirement.

LESSON 03 · 30 MIN · ONE LOCAL CHANGE

Turn a plan into a change you can review

Practice the full reasoning loop on one tiny requirement. A local diff is enough; a GitHub pull request is a separate, optional publishing step.

By the end: you can map acceptance criteria to code and tests, approve a bounded implementation, and decide whether the evidence is sufficient.

Make "done" observable

The practice function still uses the 24-hour baseline. change-request.md asks for cancellation at 2 hours or more, only for booked appointments. Invalid time values and other statuses must stay ineligible. We are not adding a database, time-zone conversion, UI, or rescheduling.

  1. Start a new worktree session from the clean baseline main. Choose Plan. Ask for the plan below without approving implementation yet.
  2. Check its file list and boundary cases against the matrix. Correct the plan if it misses the exactly-2-hours case.
  3. Approve only the local implementation with the second prompt, and select Interactive execution when asked. Inspect the proposed tool operations.
  4. Review Changes, run node --test in that session's worktree, and compare the results with the requirement.
STEP A · PLAN ONLY
Read change-request.md, booking-policy.js, and booking-policy.test.js.
Map each acceptance criterion to current behavior and propose the smallest change.
List the files, exact boundary tests, and existing behavior that must remain.
Explain which old test expectations must change because the requirement changed.
Plan only. Do not edit files, commit, push, create issues or PRs, or merge.

What a small, well-supported result looks like

The cutoff changes from 24 to 2; the booked-only and finite-number guards remain. A test that formerly rejected 23 hours must now accept it, and below-cutoff coverage moves below 2. New tests include exactly 2 and 1.99. The README states the new behavior. The Library snapshots stay unchanged because they are a separate historical evidence exercise.

A pass count by itself is not enough. Inspect the test inputs and assertions, and check that no tests were removed or skipped merely to hide a failure.

When you are ready for a real PR

A pull request proposes merging one branch into another. To practice this extra step, use your own authorized GitHub repository and connect it as the remote; a local-only folder cannot host a PR. Verify the destination first. Explicitly approve committing, pushing, and opening one draft PR. Include the requirement, changed files, test command and result, and known limitations. Leave it unmerged.

Review the PR's Files changed and Checks. If you ask for revisions, keep them on the same PR and inspect the new diff. A cloud-agent assignment means work was dispatched; it does not prove implementation or review is complete. For Jira-based teams, use the story-to-review lesson.

Before moving on

  • Exactly 2 hours succeeds; 1.99 fails.
  • Other statuses and invalid numeric inputs remain ineligible.
  • You reviewed a real diff and real test output, not just an agent's success sentence.
Quick check: all tests pass, but none tests exactly 2 hours. Is the boundary requirement demonstrated?

A test suite proves only what its assertions cover. Measure the requirement directly; do not substitute a general green badge for missing evidence.

LESSON 04 · 20 MIN · TWO BOUNDED TASKS

Work in parallel without sharing a checkout

Separate independent tasks, then prove they are isolated. Two open chats are not evidence of two independent workspaces.

By the end: you can identify a worktree's path, branch, starting commit, and diff, and explain what worktrees do not isolate.

What a worktree gives you

A Git worktree is another working directory connected to the same repository. The app can give each task a separate worktree and branch. That keeps one task's uncommitted file edits out of another task's checkout. It does not isolate ports, credentials, external systems, or all operating-system access.

Same baseline commit
Session AWorktree A / branch AA documentation-only edit
Session BWorktree B / branch BA read-only test audit

Try it

  1. Keep the policy implementation from lesson 3 in its own session. Do not reuse its checkout for this exercise.
  2. Create sessions A and B in the practice repository. Select This computer → New worktree and the same original main baseline for both.
  3. Send A's prompt, then B's. If their execution overlaps, you observed parallel execution. If one finishes first, you can still verify isolation.
  4. Run the inspection commands in each session's terminal. Compare paths, branches, starting SHAs, and diffs.
SESSION A · COMMENTS ONLY
In this worktree, add one concise documentation comment above canCancelOnline in booking-policy.js.
Describe its existing input and current rule accurately. Do not implement the two-hour change.
Change comments only. Run node --test and leave the diff for review.
Do not edit another checkout, commit, push, or create a PR.
SESSION B · READ-ONLY
Read booking-policy.js, booking-policy.test.js, and change-request.md.
List the existing test cases and the missing cases needed for the new requirement.
Cite actual assertions. Do not implement the requirement or change any files.
Do not commit, push, create a PR, or touch another session's worktree.
TERMINAL · RUN IN BOTH WORKTREES
git rev-parse --show-toplevel
git branch --show-current
git rev-parse HEAD
git status --short
git --no-pager diff --stat
git worktree list
How to interpret the evidence

A and B should have different paths and branches, but matching initial commit SHAs. A's diff should contain only a comment; B's working tree should remain clean. The separate policy-change session should retain its own diff.

Later commits on another branch do not automatically appear in a worktree. Integrate changes deliberately after review. Worktrees can still conflict when changes are merged. If two tasks need the same changing code, sequence them or use a dependency chain rather than pretending they are independent.

Before moving on

  • You recorded different paths and branches for A and B.
  • Only A has the intended edit; B is clean.
  • You can explain why separate worktrees are not a security boundary.
Quick check: two tasks edit the same checkout on different chats. Are they isolated?

Isolation is a property of the workspace, not the chat title. A shared checkout can contain edits from both tasks.

LESSON 05 · 30 MIN · TRIGGERS + TOOLS

Design an automation you can control

A Copilot app automation is not just a saved prompt: it has a trigger, execution environment, identity, tools, inputs, and a cost profile. Design those before enabling it.

By the end: you can distinguish Project recurring tasks from standalone automations, select a bounded trigger and tool set, interpret who can see and authorize a run, and pause it safely.

Choose where recurring work belongs

Project task or standalone automation?
Use a Project task whenUse a standalone automation when
The recurring work advances an ongoing goal, reuses Project context and Library material, and needs steering through the Project's Overview.A repository event or schedule should run a repeatable job with a defined prompt, trigger, tools, and execution identity.
Example: every Monday, summarize new feedback added to the Project Library and list unresolved questions.Example: on a matching issue, prepare a read-only triage report or open a draft PR after the required checks.
Review the schedule in the Project's Automations tab. Pause or delete it when the goal or input cadence changes.Review the automation card, triggers, tools, ownership, run logs, and cost controls before saving.

Both create agent work without a person starting each run. A static Library or old issue is not fresh evidence: the prompt must identify which new inputs to read and how to report missing or stale data.

Trigger and permission design

Cloud automations are not available in public repositories; their repository must be private or internal, with cloud agent and automation policies enabled. A local automation can use an approved local folder, but the computer and app must be available for it to run. A public Pages site is not an automation host.

Local

Runs from your computer and can use a local folder. Rehearse on the fictional kit, run once, inspect the output, then pause or remove the test schedule.

Cloud

Runs in GitHub's cloud, even when your computer is off. Repository policy, selected tools, identity, triggers, read visibility, and AI credit limits all matter.

Try it

  1. First run the prompt below in a normal session on the clean practice baseline. Review its output and refine the instructions before saving an automation.
  2. Open Automations → Create automation → Create manually. Name it Practice feedback digest, leave Run in the cloud off, and select the extracted practice folder or repository.
  3. Select the narrowest trigger offered for local execution. Paste the rehearsed prompt, review the model and execution settings, then choose Create and run if available. Otherwise create it and use the play button to run it on demand.
  4. Inspect the actual run and report, including source IDs, gaps, and whether it truly executed from the folder. Immediately pause or delete the test schedule so no future runs are left behind.

What should the first run show?

The kit contains four feedback records. F1, F2, and F3 concern cancellation behavior or guidance; F4 asks for rescheduling. It should cite those IDs, state that this is a fictional static snapshot, and avoid calling four records four unique customers. A completed run is evidence of execution; a saved automation card is not.

Running the prompt in an ordinary session proves only the rehearsal. It does not prove that a saved automation or an event trigger fired.

Least privilege is a configuration, not a sentence

  • Limit GitHub writes. Where the issue/PR trigger supports it, consider limiting writes to the triggering item and resources created by that run. This does not constrain MCP tools.
  • Inspect MCP separately. GitHub tools are scoped to the repository; an MCP server can reach anything its credentials and configuration allow. Select only the specific MCP tools needed.
  • Prevent unwanted loops. Decide whether events created by Copilot can trigger the automation again; set event filters and write-access requirements for untrusted input.
  • Bound cost and impact. Review per-run and recurring AI-credit limits, Actions usage, tool permissions, and the pause/delete control. Per-run credit limits stop that run; daily, weekly, and monthly limits do not stop an already running job.
  • Keep the human gate. Have the automation prepare a result or draft before enabling comments, labels, code pushes, or pull requests. Confirm the target and current state before any write.

Before moving on

  • You inspected the report from an actual saved-automation run, or recorded clearly that you only rehearsed it.
  • The report distinguishes a static snapshot from live data.
  • No unintended schedule or write permission remains enabled.
Quick check: does a Personal cloud automation make its run logs visible only to you?

Ownership and run visibility are different. Check the current permissions, identity, billing, and log visibility before saving a real workflow.

LESSON 06 · 40 MIN · ADVANCED / CONNECTED OPTIONAL

Take a Jira story to a reviewed pull request

Practice a traceable delivery workflow: story and acceptance criteria, codebase analysis, a bounded plan, implementation, test evidence, and human review.

By the end: you can explain each stage, identify its inputs and writes, keep Jira and GitHub status accurate, and stop before an unauthorized transition or merge.
Important distinction: the Jira Story Workbench in some workshops is a custom canvas/extension, not a built-in Copilot app feature. Jira access also needs an approved connection and account permissions. This guide teaches the workflow using fictional files and does not connect to a real Jira site. The workshop's demonstration extension is kept in this repository only as a reference sample; its default Jira site and project belong to the workshop's demo, so review and replace them before using it anywhere else.

The delivery stages and their gates

One story, five reviewable stages
StageInput and outputHuman gate before the next stage
1. Analyze with codebaseAcceptance criteria mapped to actual code, likely tests, risks, and open questions.Confirm the repository and source version; resolve ambiguity before planning writes.
2. PlanA file-by-file implementation plan, test matrix, and optionally linked GitHub issues.Review the scope and approve issue creation separately. Do not treat generated issues as acceptance criteria.
3. ImplementA bounded coding-agent assignment in an isolated branch or worktree.Confirm the target issue, repository, branch, and any Jira status change before dispatch.
4. Test coverageEach acceptance criterion marked covered, partial, or missing, with test evidence and gaps.Inspect actual test commands and results; ask for missing coverage before calling the story ready.
5. Pull request and reviewA PR link, checks, review findings, and a summary tied back to the story.Review the diff and blocking findings. This workflow stops before merge.

A separate Jira comment is an external write. In a custom Workbench, posting may be an explicit per-stage checkbox or a manual action. Review the exact text and issue key before posting. Optional status transitions are writes too; verify the destination state and the condition that triggers the transition.

Run the fictional lab without Jira

Use change-request.md as a mock story and the extracted practice repository as its codebase. This lets you learn the stages without an Atlassian account, extension, network access, or access to a company repository.

  1. Analyze. Map every requirement to a source file and current behavior. List test gaps, risks, and questions; do not make a code change.
  2. Plan. Ask for the smallest file-by-file plan and boundary matrix. Check that the exact 2-hour case is included and that rescheduling is out of scope.
  3. Implement. Only after reviewing the plan, use lesson 3's implementation exercise in a separate worktree. Keep issue creation, Jira writes, pushes, and PR creation off.
  4. Test. Compare actual test results to every criterion. Mark partial or missing coverage honestly; do not infer coverage from a green suite.
  5. Review. Inspect the final diff, test changes, and limitations. A real Jira update or PR is optional and requires your own authorized sandbox and separate approval.

Use only an authorized sandbox story and repository. The exact controls depend on that extension, so inspect its own instructions before acting. A typical guided Workbench orders the same stages above and can optionally post successful stage summaries back to Jira. It may also offer a status change when implementation starts or after a review without blocking findings; verify the exact trigger and target before enabling it.

Before handing off or updating Jira

  • The analysis names the exact story, repository, code evidence, and open questions.
  • The accepted plan includes each criterion and tests; created GitHub issues do not silently broaden scope.
  • The coding agent's branch, PR, and test evidence are real and linked to the intended story.
  • Any Jira comment or transition is a separately reviewed write. A failed stage or failed comment is reported, not presented as success.
  • The final review is complete, but no merge happened without a separate decision.
Quick check: the coding-agent assignment started. Is the Jira story ready to close?

A dispatched task is a handoff, not proof of completion. Confirm each stage's result and distinguish a successful code change from a successful Jira update.

LESSON 07 · 20 MIN · READ-ONLY COMPARISON

Choose models with evidence

Compare the usefulness of the result, not the confidence of the answer or the name in the picker.

By the end: you can explain Fusion, run a controlled comparison, and record unknown measurements honestly.

One task, different ways to solve it

A named model chooses the main model for your session. Copilot Fusion is a runtime router and orchestrator: it selects models, reasoning effort, and execution patterns for a task. It is not a new single model. Availability depends on your plan and policy.

Single

One model completes the task.

Cascade

A draft is judged and may be escalated.

Critique

Critics examine a draft before revision.

Standard balances cost, quality, and latency; High and Max can prioritize deeper work. More review calls can take longer and cost more. High does not always mean Cascade, and Max does not always mean Critique. Use the current documentation rather than assuming a permanent mapping.

PATHWAY A / CUSTOM WORKFLOWS

When built-in app features are not enough

A team can extend the Copilot app with connectors, skills, plugins, and canvas extensions. A Jira Story Workbench is one possible custom workflow built from these pieces; it is not included in the standard app, and installing an extension does not grant Jira access by itself.

  1. Start from the user journey. Define what the learner sees, the stages, stage results, and decisions that require a human.
  2. Inventory access. Separate read-only Jira and GitHub data from issue creation, coding-agent assignment, comments, field edits, status transitions, and merge. Name the identity and permission for each write.
  3. Design failure states. Show pending, partial, failed, and complete results distinctly. Before retrying, check whether an issue, PR, comment, or transition already happened.
  4. Test the boundaries. Use fixtures for missing criteria, inaccessible code, failed tests, duplicate delivery, blocked comments, and a PR with blocking findings. Confirm that a failed stage does not unlock the next one.
  5. Publish only approved material. Keep credentials, tenant URLs, proprietary code, and customer data out of a public extension and its examples. Review all tools and external writes before install.
For this learner guide: the example workflow is described at a high level with fictional practice data, and no credentials are included. PATHWAY B / PR LIFECYCLE

Understand Agent Merge before enabling it

PR maintenance may involve responding to feedback, repairing failed checks, and resolving conflicts. These are different from deciding that a change should merge. The app's documented Agent Merge workflow can fix blockers and merge when GitHub permits it. Do not treat its switch as a harmless "watch" button.

For learning, open an existing authorized PR and inspect its diff, checks, review threads, and available controls without enabling automation. Explain the blockers to another person. If you later enable maintenance or merging, inspect the exact action settings, repository rules, costs, and stop controls. Do not assume every app version provides a maintenance-only option.

PATHWAY C / DEPENDENT CHANGES

Use stacks when one change depends on another

Independent tasks can start from the same baseline. Dependent changes need ordering. For example, an API response field can be layer A, and the UI that consumes it can be layer B. Keep each layer reviewable with its relevant tests.

After explicit approval, use the installed stack workflow and verify the bases and membership. Changes below can require synchronization above. Merging a native stack entry can also merge lower entries. Review the entire affected chain before a separately authorized merge.

A small glossary

Repository
A project's files and tracked Git history. A local repository is not automatically published to GitHub.
Branch / commit
A branch tracks a line of work. A commit is a recorded snapshot; its SHA identifies the starting point for a comparison.
Worktree
A separate working directory tied to a Git repository, usually on its own branch. It is not a full security sandbox.
Session / Project
A session works on a task. A Copilot app Project coordinates an ongoing goal across repositories, sessions, Library material, and recurring tasks.
Automation
A saved agent task with a trigger, execution environment, identity, selected tools, and cost implications. Local and cloud automations have different availability and permissions.
Jira Story Workbench
A custom guided workflow for a Jira story. It is not a built-in app feature; Jira access requires an approved connection, permissions, and human review of external writes.
Diff / PR
A diff shows changes. A pull request proposes integrating a branch and collects discussion, checks, and reviews.
CI
Continuous integration: automated checks such as tests. A local test result and a GitHub CI run are different pieces of evidence.
MCP / skill / canvas
MCP connects tools and data. A skill supplies task-specific instructions and resources. A canvas is a shared interactive work surface.
Acceptance criterion
A concrete condition that demonstrates the requirement, such as "a booked appointment exactly 2 hours away can be canceled."

When something does not work

A feature, model, or connector is missing.

Check the official prerequisite page, your app version, and organization policy. Ask your administrator rather than bypassing a restriction. Read the worked example or use an available alternative, and label what you did not run.

New worktree is unavailable.

Confirm you opened the extracted kit as a Git repository and created the initial commit. A plain folder has no branch history to base a worktree on. Do not substitute Current checkout when testing isolation.

The original tests pass but the new behavior does not.

The baseline tests intentionally describe the old 24-hour rule. Inspect the requirement, update obsolete expectations, and add boundary and regression tests. Do not delete or skip tests merely to obtain a green result.

The agent does too much or invents evidence.

Stop and narrow the scope. Name the source files, output format, and allowed actions. Ask it to distinguish observed facts from proposed work. Read the sources and actual diff yourself.

The Copy button or saved notes do not work.

Browser privacy settings can block clipboard or storage access. Select prompt text and copy it manually. Keep the tab open and export your notebook before leaving; saving locally is not a cloud backup.

I cannot create a cloud automation in a public repository.

Current GitHub documentation restricts cloud automations to private or internal repositories with the required policies enabled. Complete the local exercise instead, or use your own approved private practice repository. Do not make a company repository public to work around an access issue.
