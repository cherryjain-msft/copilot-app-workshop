    Learn when to use Projects, Automations, Jira Workbench, parallel worktrees and Copilot Fusion. Follow the examples with a fictional Dealer Service Booking app, try the copy-ready prompts, and check what happened before moving on. A pull request (PR) is how you propose code changes for review.

    Before you try the exercises

    You can read every lesson without signing in. Hands-on exercises need the Copilot app, the relevant feature enabled for your account, and access to the repositories you use. Local app exercises need Node.js 20+ and Git. The Jira lesson explains its additional connector requirements. Use your own practice copies for changes to shared repositories.

    How to use this guide

    1. Read what the feature does and when it helps, then try the steps in your own environment.
    2. Review each prompt before sending it. Replace sample repository names and Jira keys where indicated.
    3. Compare your result with the expected outcome. Use the notes below each lesson for questions and key takeaways, then mark the lesson complete.

    If a feature or repository is unavailable, you can still study its explanation, diagram and example output. Reading an example is different from running the exercise.

    One story, one owner

    The Workbench exercise owns the EV story, while parallel sessions and Fusion use separate tasks without implementing it again. Projects and Automations use the separate, fictional cancellation rollout; automation reports reuse its existing PRs. If work already exists, resume it rather than creating a duplicate. Reading this guide or copying a prompt does not launch agents, automations, PRs or merges.

    How the features fit together

    A Project coordinates a goal across repositories and reference files. An automation repeats a saved task. The custom Jira Workbench guides one story toward a reviewed PR. Worktrees give independent sessions separate working copies, while Fusion chooses models within a task. Human review remains important throughout.

    Turn on Learning tips for extra explanations and alternatives when an exercise is unavailable. Arrow keys move between lessons unless you are typing in a field. Copy copies a prompt; it does not run it. Your notes and completion are stored only in this browser.

    Core lesson · 1 of 5

    Projects: from shared context to decisions

    A session works on one task in one checkout. A Project holds a longer-running goal: the repositories involved, the files that define what’s correct, and the sessions it starts. In this lesson, you’ll investigate a question that no single repository can answer.

    Choose 1.1: investigate across repositories or 1.2: turn scattered Excel files into a decision dashboard. The second exercise uses only Library files.

    1.1 · Service cancellation across three repositories

    When a Project helps

    Cross-repo investigation Try this first

    Trace one customer problem through the API, front end and help content that share it.

    Coordinated change

    Agree on one fix, then start a session per repository in the right order and follow them from Overview.

    Policy or pricing rollout

    Check every customer-facing surface against an approved brief, before and after launch.

    Research before code

    Repositories are optional. Group customer feedback in the Library by theme before anyone changes code.

    Comment permission must cover the associated PR

    A workflow-run event is not itself a PR. This comment variant needs policy-approved repository write scope; do not assume trigger-only workflow-run scope permits PR comments. The prompt limits intended writes to the associated PR, but it does not enforce that boundary at the server. If policy or the team rejects that broader grant, use a read-only run report and explicitly mark the comment variant unavailable.

    Optional third-party MCP: Jira impact context

    If the PR explicitly names a Jira story, an approved cloud-available Jira read connector can add its business impact and acceptance criteria to the diagnosis. A connector signed in on your desktop is not automatically inherited by cloud automation. The kit explains the access checks; this optional cloud connection has not been configured or verified.

    If this PR explicitly references a Jira story and the approved cloud Jira read tool is available, read its summary and acceptance criteria to add business impact to the CI response. Otherwise state why Jira enrichment is unavailable. Do not write to Jira.

    Other repeatable team workflows

    Consider scheduled Excel data-quality checks with an exception dashboard, cross-repo policy/documentation drift reports, or triage whenever an issue receives a bug label. These are extension ideas, not configured jobs; check tool access and approve any writes before enabling them.

    Execution, ownership, and safety

    The local workflow needs your app and computer available. The cloud shared job can react while your computer is off and is billed to the repository owner; its ownership is fixed at creation. Neither a prompt nor a linked repository expands tool access.

    Check existing automations, live tools/triggers, repository policy and actor eligibility before saving. Only the shared job gets an approved comment write, with the scope tradeoff described above; neither job may merge or change code. Refresh inputs before using them for a real decision. Outputs must distinguish synthetic data, snapshots and live reads.

    Full setup and repeat-run guidance are in automation-prompts.md. Keep unavailable event results marked not observed yet. Pause any old weekly follow-up schedule separately if you no longer want it.

    Understand the execution patterns

    Single

    One model completes the task.

    Cascade

    A draft is judged, then accepted or escalated to a stronger model.

    Critique

    Independent critics review a draft; their feedback informs a revision.

    A higher tier is not a guaranteed outcome

    High does not always mean Cascade, and Max does not always mean Critique. Fusion selects patterns per prompt when warranted. Review calls can take longer and cost more. Compare the actual results rather than assuming a higher tier will be faster, cheaper or correct.
