    Learn when to use Projects, Automations, Jira Workbench, parallel worktrees and Copilot Fusion. Follow the examples with a fictional Dealer Service Booking app, try the copy-ready prompts, and check what happened before moving on. A pull request (PR) is how you propose code changes for review.

    Before you try the exercises

    You can read every lesson without signing in. Hands-on exercises need the Copilot app, the relevant feature enabled for your account, and access to the repositories you use. Local app exercises need Node.js 20+ and Git. The Jira lesson explains its additional connector requirements. Use your own practice copies for changes to shared repositories. The slides are optional and require separately granted Microsoft sign-in and file access.

    How to use this guide

    1. Read what the feature does and when it helps, then try the steps in your own environment.
    2. Review each prompt before sending it. Replace sample repository names and Jira keys where indicated.
    3. Compare your result with the expected outcome. Use the notes below each lesson for questions and key takeaways, then mark the lesson complete.

    If a feature or repository is unavailable, you can still study its explanation, diagram and example output. Reading an example is different from running the exercise.

    How the features fit together

    A Project coordinates a goal across repositories and reference files. An automation repeats a saved task. The custom Jira Workbench guides one story toward a reviewed PR. Worktrees give independent sessions separate working copies, while Fusion chooses models within a task. Human review remains important throughout.

    Turn on Learning tips for extra explanations and alternatives when an exercise is unavailable. Arrow keys move between lessons unless you are typing in a field. Copy copies a prompt; it does not run it. Your notes and completion are stored only in this browser.

    One problem, three repositories

    A session works on one task in one checkout. A Project holds a longer-running goal: the repositories involved, the files that define what’s correct, and the sessions it starts. In this lesson, you’ll investigate a question that no single repository can answer.

    When a Project helps

    Cross-repo investigation Try this first

    Trace one customer problem through the API, front end and help content that share it.

    Coordinated change

    Agree on one fix, then start a session per repository in the right order and follow them from Overview.

    Policy or pricing rollout

    Check every customer-facing surface against an approved brief, before and after launch.

    Research before code

    Repositories are optional. Group customer feedback in the Library by theme before anyone changes code.

    Two automations, two kinds of ownership

    An automation repeats saved instructions on a schedule or in response to an event. In this lesson, compare a personal weekly report with a repository-shared report triggered by a pull request. Both examples are cloud-based and read-only; ownership and execution location are different choices.

    Use a practice repository where you have permission to manage automations. Check for an existing automation with the same purpose before creating another. If you use your own workshop copy, select that repository throughout both exercises.

    Use caseOwnership and triggerWhat it does
    My weekly follow-up queueCloud, Personal; weekly scheduleSummarize issues assigned to me and PRs I authored or need to review.
    PR intake snapshotCloud, Repository; pull request openedCheck the PR summary and visible check state; report evidence and unknowns, with no writes.

    1. Personal: weekly follow-up queue

    1. Open Automations → Create automation. Choose your practice repository, cloud execution, and Personal ownership.
    2. Name it My weekly GitHub follow-up. Set a weekly schedule, for example Monday at 15:00 UTC, and grant only GitHub issue and pull-request read tools.
    3. Use the prompt below and review the settings before saving. Run it once to inspect the output, then check its next scheduled run. Pause the schedule after practicing unless you want it to continue.
    Build my weekly follow-up queue for this repository using the automation owner's GitHub identity.
Find open issues assigned to me, pull requests authored by me, and pull requests where my review is requested. Use the corresponding @me search filters.
For each result, include its link, title, last activity, current review or check state when available, and one concrete next step. Deduplicate results.
If an identity filter fails or data is unavailable, report the limitation; do not broaden the search to all repository work. Distinguish a successful search with no results from unavailable data.

Return the report in this run only. Do not edit files, comment, assign, label, request reviews, approve, merge, or push.

    2. Shared on the repository: PR intake snapshot

    1. Create PR intake snapshot for the same practice repository with Repository ownership and cloud execution.
    2. Choose Pull request opened as the trigger, filtered to app/**. Grant only pull-request read access and repository-file read access for .github/pr-checklist.md.
    3. Use the read-only prompt below. A matching PR from the Workbench lesson can provide the event if its actor is eligible under the trigger policy. Do not open a duplicate PR just to test the trigger.
    Review only the pull request that triggered this run.
Read its live title, description, base and head branches, issue references in the title or description, and current status-check results. Read .github/pr-checklist.md.
Report whether the title or description includes a Jira key and one-line summary. List checks as passing, failing, pending, or unknown with links when available.
For checklist items that require inspecting a code diff, running tests, or other evidence you cannot access, mark unknown and explain why. Do not infer a pass from missing evidence or a passing check alone.
Return a concise table of item, result, and evidence, followed by unresolved questions. This is an advisory report, not a merge gate.

Return the report in this run only. Do not comment, change labels, request reviewers, approve, push, or merge.

    Execution, ownership, and safety

    Cloud execution lets these examples run without your computer staying on. Scheduled or manual tasks can also run locally; GitHub event triggers require cloud execution. Personal cloud automations are visible only to you, run using your identity, and use your AI credits. Repository automations are shared with the repository and billed to its owner. Cloud prompts and logs are visible to repository readers, even for personal automations. Ownership cannot be changed after creation.

    Before enabling a trigger, check repository policy, visibility and whether the event actor must have write access. Copilot-created PRs also need the trigger to accept Copilot activity; do not assume every new PR can start a run. Keep tool grants read-only. A report is not approval to change code or merge.

    Full copy-ready prompts and settings are in automation-prompts.md. If no eligible PR has opened since you enabled the trigger, leave the event result as not observed yet.

    Check your result

    • The personal report lists your relevant work or clearly states that no results were found.
    • The shared report identifies the triggering PR and separates evidence from unknowns.
    • You can explain the difference between ownership, execution location and trigger. A manual run alone does not prove an event trigger worked.

    Key idea: Personal helps you follow up on your work; shared gives the team a consistent report. Neither example has permission to make changes.

    If blocked: Review the saved instructions and trigger settings to understand the design. Keep unavailable data marked unknown, and pause any schedule you do not intend to keep using.

    Compare the result, not the label

    Fusion is a runtime model router and orchestrator, not a single model. It selects models, reasoning effort and execution patterns, then returns one final response.

    ChoiceWhat you controlWhat it prioritizesUse in this exercise
    Named modelSelect an available model and reasoning effortA fixed model selection for the main agent; delegated tools/agents are separate.Baseline, not an assumed winner or loser.
    Fusion StandardSelect StandardBalances cost, quality and latency; selects one model for each task.Everyday-work comparison.
    Fusion HighSelect HighBalanced orchestration for substantial, well-scoped work.Compare with the named model.
    Fusion MaxSelect Max if availableDeep reasoning and thorough analysis while considering token efficiency.Optional extended comparison.

    Understand the execution patterns

    Single

    One model completes the task.

    Cascade

    A draft is judged, then accepted or escalated to a stronger model.

    Critique

    Independent critics review a draft; their feedback informs a revision.

    A higher tier is not a guaranteed outcome

    High does not always mean Cascade, and Max does not always mean Critique. Fusion selects patterns per prompt when warranted. Review calls can take longer and cost more. Compare the actual results rather than assuming a higher tier will be faster, cheaper or correct.

    Set up a fair, repeatable comparison

    1. Record a baseline commit before the EV implementation is added using git rev-parse HEAD. Use fresh, clean sessions at that same commit with the same repository instructions and files.
    2. Keep environment, permissions, tool access, session mode and prompt identical. No Jira access, previous conversation, extra hints or manual edits for one contender only. Do not delegate separate agents.
    3. Start with one named model and Fusion High if available. You can add Standard and Max to extend the exercise. Each run uses credits. These are comparison sessions, not the Workbench delivery session.
    4. Time from sending the prompt to its final response. Note approvals or connection delays. Hover the response's effort label to inspect actual models used. If a pattern or credit total is not exposed, record not shown.

    Optional lesson · A

    Optional lesson · B

    Small reviews for dependent changes

    Independent work branches from the same baseline. Dependent work forms a stack: the upper PR targets the branch below it, so each review shows one layer.

    mainUltimate base
    ←
    PR A · API + testsBase: main
    ←
    PR B · UI + testsBase: branch A

    Practice with a separate follow-up

    Use a new, unstarted follow-up: show estimated service duration in booking confirmation. Layer A adds an additive durationMin field to the booking response, with tests and API docs. Layer B consumes that field in the confirmation UI, with tests. Check whether this work already exists before selecting it.

    If you choose to implement the exercise, explicitly approve opening the two PRs using the app's pr-stack skill in your practice repository. Create layers sequentially, bottom to top: A must commit and push before B's worktree snapshots A. Each layer owns its branch and opens its PR in the app.

    Inspect the base branches and diffs

    1. Open the bottom PR and confirm its base is main with an API-only diff.
    2. Open the top PR and confirm its base is branch A, not main. Its review should show only the UI layer.
    3. Explore stack navigation if native registration is supported. A dependent branch chain alone is not proof of registered native stack metadata.
    4. Notice that a lower-layer change may require rebase/sync and renewed checks above it. Keep changes in the owning sessions; do not force-push another active session's branch.
    Keep merging outside this exercise

    Native stacks can have cascading merge and queue behavior. Review the full membership, ordered bases, checks and protections before any separately authorized merge action. Cross-fork PRs are not eligible for native stack registration; a dependent-PR chain without registration is still a different result.

    Key idea: A stack makes dependencies explicit and reviews smaller. Independent changes usually do not need a stack.

    Check your understanding: Explain why the top PR targets branch A rather than main, and what may need updating if A changes.
